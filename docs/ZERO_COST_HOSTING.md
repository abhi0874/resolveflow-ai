# ResolveFlow AI zero-cost hosting feasibility

Reviewed 2026-11-21. **Feasibility assessment complete. Public full-account staging is blocked.** The source review found a possible no-charge architecture, but did not establish the provider availability, identity setup, and recovery guarantees needed to recommend it for public use.

## Evidence and non-negotiable requirements

Step 6C ran the full stack in an isolated Linux ARM64 guest. The integrated run reached 1.95 GiB of cgroup memory and a one-second CPU peak of 3.09 cores with a four-CPU limit. The same-version CPU-only PyTorch build occupied 1.11 GiB for Python and reached 1.62 GiB in the integrated run and 2.83 GiB including backend tests. It kept the sampled MiniLM vectors unchanged. These are whole-stack observations, including file cache, rather than per-service bounds or availability promises. Both variants passed 115 backend tests and a Chromium smoke. SMTP and Google used test infrastructure. [Step 6C summary](PROJECT_STATUS.md#account-expansion-step-6c-retry--isolated-linux-acceptance)

The verified deployment uses a persistent queue dispatcher and RQ worker, PostgreSQL/pgvector, private POSIX files, a Restic repository, and a deletion journal plus a commit witness on separate filesystems. Recovery requires a trusted current seal, rejects uncertain histories, and leaves the target quarantined. Transactional identity emails rely on the dispatcher and worker. Signed, fresh Google `auth_time` is required for Google-account deletion. ## Service decomposition and cost decision

Separating Next.js from FastAPI is technically plausible with a reviewed same-origin proxy, and can move the web tier to Vercel Hobby for personal use or Cloudflare Workers Free. That leaves native ML packaging, long-lived RQ execution, persistent private storage and deletion-safe restoration unresolved. Replacing RQ with event-triggered consumers would be a separate implementation requiring tests of durable retry, idempotent delivery, and credential revocation across interrupted jobs. Pointing the app at external DB/object storage is also a migration. Current backup tooling expects a controlled loopback source and an owned quarantined restore target, and the erasure journal uses a filesystem witness. Neither change was validated at this step.

The strongest **conditional** public design is a single OCI Always Free A1 (2 OCPUs, 12 GB RAM) for Caddy, Next.js full mode, FastAPI, local PostgreSQL 18/pgvector, authenticated Valkey with AOF, RQ, CPU-only PyTorch, and private file storage. Use the free block allocation for boot/state and a separate witness filesystem. Use Brevo Free, a provider-approved no-cost delegated hostname with free authoritative DNS and Caddy/ACME, Google OIDC with verified additional claims, and capped no-payment B2 for independently retained encrypted archives. Keep local and independent key escrow. The target is **$0/month within verified allowances**. A card for Oracle registration may be required. Hosted spend, egress/IPv4 entitlements for the chosen region, capacity, hostname approval and off-host recovery are unresolved. Reject any option that requires a paid upgrade or an overage-enabled account. A separate volume on the VM is only the live witness and does not meet independent recovery custody by itself. The latest authoritative seal must survive independently, and recovery stays closed if it cannot be proven current.

## Approval and verification before trying the conditional design

1. Obtain explicit scope for provider registration and card verification if required, chosen OCI home region and test cohort, DNS delegation/account hostname, public privacy/support page and Google consent publication, Brevo sender setup, B2 archive policies and a named recovery operator. Require $0 limit behavior and a non-upgraded tenancy. Record allowed CPU/RAM, boot/witness sizes, IPv4/egress, and backup quotas from the account before creating resources. Stop if capacity or billing cannot be confirmed.
2. Rehearse the same CPU-only Torch 2.14.1 on two CPUs with the locked stack. Run concurrent login, document indexing, retrieval and queue work with one worker. Record peak memory, P95 response time, queue drain and disk high-water marks. Keep real classification/retrieval. Any live Gemini testing needs existing opt-in and a verified non-billed quota. Review a targeted Linux CPU index lock before approving any release bundle. The repository lockfile currently remains unchanged.
3. Only after explicit provisioning authorization, configure tightly scoped SSH, private loopback upstreams, the exact callback and origin, TLS, private encrypted directories, a separate mounted witness, disposable staged database and synthetic accounts. Use [staging service procedures](HOSTED_STAGING.md#reproduce-the-staging-installation-after-approval). Supply DNS update credentials, DB and Valkey credentials, OAuth client secret, SMTP key, B2 scoped keys and escrowed recovery material through a protected operator channel.
4. Verify HTTPS renewal and denied ingress, successful sign-in, valid/stale/missing `auth_time`, replay rejection, verified inbox delivery, password recovery, profile updates, session revocation, permanent deletion and tenant isolation. Stop and restart the worker/broker with queued work. Capture an encrypted pre-deletion backup, complete a deletion, deposit independently authenticated current evidence, and restore on a second isolated host with the source inaccessible. Confirm missing/stale seals and ambiguous ownership fail closed. Keep staging private until verification. [Acceptance gates](HOSTED_STAGING.md#mandatory-staging-acceptance-gates)

## Recommended $0 service-cost alternative now

Keep the existing Vercel personal recruiter showcase public on its provider HTTPS URL. Run the complete app privately using already-owned hardware, loopback Next.js/FastAPI, PostgreSQL/pgvector, Valkey/RQ, pinned local classification and MiniLM, Mailpit, and Restic on existing private storage. This has **$0 in new monthly service subscriptions and no new payment-card requirement**. Hardware, electricity and connectivity are existing operator inputs. Mailpit provides synthetic verification/recovery delivery, and Step 6C's signed fixtures exercise Google sign-in and reauthentication locally. Live public Google and email are outside this fallback. It leaves the production signup boundary closed.

1. Use the existing [local install and startup instructions](../README.md#local-setup) against fresh operator-approved or disposable data. Keep providers offline by default. Use a bounded Linux CPU rehearsal rather than altering development data.
2. Follow [Mailpit setup](EMAIL_DELIVERY.md), [Google signing fixture and consent guidance](GOOGLE_SIGN_IN.md), and the [local encrypted backup and deletion recovery procedure](BACKUP_OPERATIONS.md). Keep backup keys and current deletion evidence on separate trusted storage, using existing operator-held media when available.
3. Run synthetic registration/recovery, Google fixture sign-in, indexing/search and deletion tests, plus a quarantined restore. Share the existing showcase link for recruiter access. The full account application remains private and runs real local ML. The synthetic site has no public signup, live user data, or worker process.
