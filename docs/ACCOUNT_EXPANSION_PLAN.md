## Architecture and hosting decision

**Extend FastAPI/PostgreSQL and add Google as a sign-in method.** FastAPI remains the account, session and workspace authority. Use a maintained OIDC client, with Authlib as a candidate subject to Python 3.14 and provider contract tests. Use a separate HTTPS origin for a Next.js full-mode build. The browser accesses an allowlisted same-origin proxy and a host-only session cookie. FastAPI runs as a container service with persistent managed PostgreSQL, and its ingress accepts the web tier through private networking or an authenticated server-only proxy boundary. The web proxy alone sets or forwards trusted service metadata. Never derive an IP rate-limit key directly from an untrusted forwarding header. Configure both per-identity and bounded global Argon2 work in addition to trusted ingress limits, because the current direct peer can represent the shared proxy. [Authlib OIDC and PKCE](https://docs.authlib.org/en/stable/oauth2/client/http/index.html)

| Option | Benefits | Costs and fit |
|---|---|---|
| Existing FastAPI + Postgres + Google | Reuses recovery, sessions, grants, user IDs and email verification. Keeps deletion and account/link invariants within the application database. Existing Next.js proxy can be extended. | Own protocol integration, abuse controls, migrations and operations. Requires separate API hosting, persistent DB and a working mail delivery path. Recommended. |
| Managed auth, e.g. Auth0 | Managed provider login, password flows and token infrastructure. Can front FastAPI via a stable provider-subject to local-user binding. | Still needs API hosting, local workspaces, local revocation and deletion coordination across two systems. Credential migration or password resets, provider key rotation, refresh-token revocation and duplicate identities add work. Auth0 advertises up to 25,000 monthly active users on Free, but its plan table excludes account linking on Free. Supabase Auth Free lists 50,000 MAU and 500 MB Postgres, but the documented same-email auto-linking conflicts with the requirement. Do not use that default. Supabase Postgres alone can be assessed separately. [Auth0 plans](https://auth0.com/pricing?bb=192670) · [Supabase plans](https://supabase.com/pricing) · [Supabase linking semantics](https://supabase.com/docs/guides/auth/auth-identity-linking) |

**Hosting recommendation.** Keep the current showcase deployed and disconnected. Later, host the new full-mode Next.js app on a separate Vercel project or next to the backend on a container host if private networking is easier. For a small, noncommercial account pilot, use a bounded FastAPI container and a separate Neon Postgres project with pgvector and TLS. Use separate migration/runtime roles. Keep direct database connections for migrations and code using session-level advisory locks, including the current workflow checkpoint and worker paths. Transaction pooling is only suitable after testing each workload's connection behavior. Run the existing mail outbox dispatcher and worker plus a compatible broker for dependable recovery. Keep uploads disabled until private persistent storage is integrated, and keep live inference off. For authenticated ML/RAG, stage the unchanged model artifacts, validate memory and restart behavior, and add private file storage and worker services before enabling those routes. ## Experience, components and acceptance gates

1. **Protected baseline and password flow.** Start with the existing Next.js auth pages and form components, `session-api.ts`, `server-api.ts`, the API allowlist, and the FastAPI auth/identity services. Gate the new account site's private pages in a shared server-side layout, and independently protect every direct API and worker action. A signed-out visitor goes to sign-in or sign-up. Keep launch and deep-link redirects on the same origin. Only a signed-in, eligible account reaches persisted personal workspaces. Gate: direct URLs/API calls, prefetch and cross-tenant IDs do not leak data; browser refresh preserves the right user; logout/recovery invalidates prior sessions; production cookies, verification mail, CSRF and account/IP rate limits work. Run current auth and demo regression tests in isolated services. No backend permissions depend on client navigation.
2. **Google OIDC.** Add dedicated start/callback handlers with explicit methods and bounded query fields, leaving the generic proxy redirect policy intact. Keep the callback on the account origin. POST initiation is protected with the existing CSRF flow, then sends the browser to a fixed provider authorization endpoint. Use authorization code, S256 PKCE, random state and nonce, short-lived single-use server-side flow state bound to the browser session/action, and an exact HTTPS redirect URI. Validate signature against Google's JWKS and check issuer, audience/authorized party when relevant, expiry, nonce, subject and provider verification claims. Consume state once and redirect to a clean same-origin URL. Store an identity row keyed by canonical `(issuer, subject)`, linked to the existing internal UUID. Never persist OAuth tokens for sign-in or request offline access. Make password hash nullable with a safe guard for stored hashes and treat Google-only password login/reset as unavailable without revealing account type. A new Google signup proves the address through the existing verified-mail system before private access, which preserves the production email proof policy even for third-party Google addresses. A matching existing email never grants access or links anything. Direct that user to the established sign-in method and require signed-in, recently reauthenticated, explicit linking plus proof of the new provider. Reject link collisions and prevent removal of the last usable method. Gate: state/nonce/PKCE and claim failures, replay, provider denial, conflicting email/sub, concurrent registrations, expired flow, wrong-user linking, verified Google signup and legacy password flows. [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect) · [Google claim verification](https://developers.google.com/identity/sign-in/web/backend-auth)
3. **Personal settings.** Introduce `/app/settings/account` and authenticated profile/settings handlers, plus schemas and a migration after 0012. Extend the shell and response types to show bounded, escaped display name, optional avatar/initials and linked methods. Treat a personal workspace as explicit creation or an idempotent onboarding action, with owner membership created in the same transaction. Start with initials plus a supported provider picture if it can be rendered under an approved policy. Add uploads only with private storage, MIME/size checks, image re-encoding and metadata stripping. For email change, require recent proof, verify the new address using a pending, expiring intent, keep the old address until atomic commit, notify the old address, invalidate stale email tokens/invitations and revoke sessions. For password change, verify the old password, enforce the same policy and revoke sessions. Google-only users see their actual available methods. Gate: mobile/keyboard/error states, duplicate or concurrently claimed email, unsafe avatar inputs, no unauthorized user read/write and credential revocation.
4. **Permanent deletion.** Add a dedicated Danger Zone, read-only impact preview, typed confirmation and recent single-use reauthentication proof bound to the account, current session, credential version and deletion action. Use password challenge when applicable. For Google-only accounts, validate the same linked subject with a verified fresh `auth_time` when supported. The implemented Google-only deletion policy refuses missing or stale provider proof. Email recovery does not authorize account deletion. Ordinary account selection, OAuth code issuance, and consent are insufficient proof of recent authentication. Gate: reject stale proof, wrong user, invalid CSRF and replay; ownership races leave an owner; all tabs/sessions and in-flight auth callbacks lose access; shared records survive with sanitized attribution; queued work is fenced and cleanup can safely resume after a crash. [Google session metadata](https://developers.googleblog.com/enhance-security-and-trust-new-session-metadata-in-sign-in-with-google/)
5. **Hosted acceptance.** Deploy only under separate authorization after testing 0012 → new migrations on disposable Postgres, mail delivery/reset from a real inbox, Google consent and callback on a stable staging origin, restart durability, quota handling, deletion and restore rehearsals. Exercise signed-out deep links, mobile/keyboard, sign-up, both sign-ins, recovery, profile changes and deletion in Playwright. Check logging redaction, retry paths and steady-state memory. Keep the standalone recruiter deployment available on its existing URL.

## Deletion transaction and retention

- Show which workspaces must be transferred or closed before confirmation. Block deletion for a sole owner of a shared workspace until an eligible successor explicitly accepts or another verified owner exists. Never silently promote a user. Recheck under the same workspace-row locks used for owner changes. A personal workspace can be removed only through explicit closure after proving it contains no other members' data. If closure is not implemented, stop with a clear prerequisite. Cancel outbound invitations and unassign tickets before removing the composite membership FK.
- Use an additive migration to handle restrictive user references from notes, activity, documents, draft/review records, workflow executions and jobs. Preserve authorized shared records and replace identifying attribution with a neutral label or nullable actor reference where appropriate. Review JSON activity details, checkpoints, indexes, exports and free text for identity copies. Update joins and response schemas before deleting the user row. Keep approved workspace content within its retention policy.
- In one database transaction lock and revalidate account, credential proof and affected workspaces. Revoke sessions, invalidate reset/verification/OTP/provider flows, remove identity and profile rows and schedule deduplicated cleanup tasks. Prevent racing OAuth callbacks from restoring access or auto-registering during deletion. Fence user-initiated queue work against current account state before external or database effects. Use a deletion operation ID and bounded retries for external storage; lost responses and duplicate requests must have a safe repeat outcome. New explicit registration later gets a new UUID and no former memberships. Never restore sessions or identities from backup without replaying deletions first.
- Disclose exactly what is retained, why and for how long before irreversible confirmation. Examples may include sanitized shared operational history and time-limited backup copies. Keep access restricted, minimize personal identifiers and let backups expire under a defined retention policy. If a future integration stores provider grants, remove or revoke the application's grants during cleanup. Deleting ResolveFlow AI data does not delete the Google account.

## Step 5B implementation and staging conditions

Personal settings now show a deletion impact preview. An empty, singly owned workspace may
close with explicit confirmation. An owner must transfer a populated workspace or one with
other members to another active owner. Workspace contents, private team documents and shared
history are retained. Historical attribution uses a disabled identity without credentials or
memberships where the shared record needs a foreign key. Unstructured team content is retained
under workspace control. The profile picture is part of the deleted PostgreSQL user row.

A password check or a signed Google authentication event during the deletion ceremony grants a
short-lived, session- and credential-version-bound proof. A confirmation challenge is kept in
browser memory and only its digest in PostgreSQL. Final submission also requires the exact text
`DELETE` and CSRF validation. Google must return the verified linked subject and a fresh
`auth_time`. Missing or stale claims fail closed. Re-registration after deletion creates a new
identity without previous workspace access. The external Google account is unaffected.
[Google session claims](https://developers.google.com/identity/openid-connect/openid-connect)

Account erasure and the file-cleanup receipt commit together. Tokens, sessions, provider
bindings, identity mail and profile fields are removed. In-flight email or workflow execution
can temporarily block deletion. Queued jobs for erased requesters are cancelled and their
delivery IDs invalidated. Receipts retain an opaque account UUID and deletion time. Google
accounts also leave a subject digest to reject older callbacks. Receipts with unverified
files retain private ownership evidence for review. These records have no sign-in capability.
[Mailbox review procedure](INVITATION_MAILBOX.md)

Existing backup copies, previously delivered email and unassigned historical files can
outlive the active account. There is no guaranteed calendar date for physical deletion from
operator-held backups. The supported restore command quarantines its disposable target before
import. The API, RQ database path and direct LangGraph checkpoint connection refuse
quarantined targets. See the [deletion recovery procedure](BACKUP_OPERATIONS.md#account-deletion-recovery)
for independent deletion records, private-file holds and supported recovery boundaries.

## Hosted account staging requirements

Use a dedicated HTTPS hostname and full-mode Next.js server. One small always-on Linux VM
can run the web server, private FastAPI process, RQ worker, dispatcher and private Valkey.
Use persistent PostgreSQL with pgvector and an operator-managed migration role. A managed
database reduces maintenance if budget permits. Size memory for the loaded models and
worker concurrency in a rehearsal. Budget for persistent volumes, encrypted off-host backups
and transactional email. Sleeping services or ephemeral disks are unsuitable for this topology.
[Example free hosting limitations](https://render.com/docs/free)

- Supply the account hostname, DNS/TLS ownership and service budget. Expose only the HTTPS web
  ingress. Set `NEXT_PUBLIC_APP_MODE=full`, private `API_INTERNAL_URL`,
  `RESOLVEFLOW_ENVIRONMENT=production`, exact trusted/CORS HTTPS origins and server-only
  `DATABASE_URL` and `RESOLVEFLOW_REDIS_URL`. Keep live AI disabled. Run the worker and
  dispatcher continuously for queued mail and workflow delivery. Keep uploads outside the web
  root on persistent private storage shared only with authorized services.
- Register a dedicated Google Web client with the exact callback
  `https://<chosen-account-host>/auth/google/callback`. Set `RESOLVEFLOW_GOOGLE_ENABLED`,
  `RESOLVEFLOW_GOOGLE_CLIENT_ID`, `RESOLVEFLOW_GOOGLE_CLIENT_SECRET` and
  `RESOLVEFLOW_GOOGLE_REDIRECT_URI`. Configure the verified app/client for additional claims.
  Google documents an essential `auth_time` claim and says apps cannot request Google Account
  reauthentication. Account selection, consent and a newly issued token do not advance it.
  ResolveFlow requires the signed time to fall after the deletion ceremony starts and no later
  than token issuance and the current time. A whole-second timestamp whose ordering is uncertain
  is rejected. A superseded transaction cannot grant proof. Validate actual claim delivery,
  recent and stale Google sessions, cancellation and clock synchronization with staging test
  accounts. Ordinary sign-in does not require this claim.
  [Google security bundle](https://developers.google.com/identity/siwg/security-bundle)
- Supply a verified sender domain and authenticated TLS SMTP credentials through the private
  settings listed above. Configure SPF, DKIM and DMARC, then test inbox delivery, verification
  and recovery with a designated staging recipient. Mailpit covers only the local delivery path.
- Before enabling deletion, migrate to 0017, provision the independent journal and witness,
  escrow the recovery keys and establish custody of the latest trusted seal. Verify a fenced
  off-host restore, storage permissions and file holds before connecting the restored services.
  Keep the public showcase on its existing origin.
